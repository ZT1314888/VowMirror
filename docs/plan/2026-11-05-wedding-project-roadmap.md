计划日期：2026-11-05。源码基线：VowMirror 主分支。
实施前，原分支 `docs/architecture-blueprint-phase2` 与本地 `main` 的提交差异为 `0 / 0`；清理与开发基础从 `main` 建立 `refactor/wedding-foundation`，交付审查时尚未提交、推送或公开部署。
用户此前授权实施并提交、推送 **Phase 0–Phase 1 清理与开发基础**。2026-11-14 本轮授权完成 Phase 2 素材接收与验收调整；Phase 3–Phase 8 仍须对应实施指令，真实模型调用须单独指令。本轮按阶段流程提交并推送 Phase 2，不部署、不合并 `main`，也不调用模型。

## 目标与执行规则

原仓库演进并保留 Git 历史；清除旧图库与单人产品，保留可复用云端协议、图片校验和安全组件，先交付全 Docker 开发环境，再逐阶段验证婚礼双人合照生成。

1. 按 Phase 0 → Phase 1 → Phase 2……依赖顺序推进。每个任务单独编号，状态为“未开始／进行中／通过／阻塞”。
2. 每个 Phase 完成任务后先验证，再判定完成；验证失败先停止推进、修复重验。记录阻塞不代表通过，不得推进依赖阶段。
3. 模拟只证明代码路径和请求契约，不证明真实效果、速度或费用；不以历史蓝图记录代替本轮证据。
4. Go 工具、依赖下载、测试、vet、格式化、构建全部在 Docker 中执行，宿主机不安装 Go 或 GoFrame CLI。依赖准备在测试计时前完成；整条 Go 测试执行 `timeout -s TERM -k 2s 58s go test -count=1 -timeout=55s ./...`，包含终止宽限期不超过 60 秒。
5. 使用真实模型前必须单独取得调用指令；不使用旧服装图、虚构婚礼素材或假成功结果填补输入缺口。
6. 本轮只接收素材和调整阶段验收，没有婚礼生成按钮、真实模型调用或正式整站改版。用户未回复不视为授权。

## 目标接口与数据边界（目录已实现，生成属于后续计划）

入口 `http://localhost:3000`；Nginx `/api/` 转发后端 `:8000`。健康 `GET /api/health` 不调用模型，不返回配置或凭据；目录 `GET /api/catalog/outfits` 和生成 `POST /api/tryon/couple` 需要 Token。旧 `/tryon`、`/comfyui/health`、Hello 无兼容入口。
JSON 请求字段：`couple_image`（Base64/Data URL）、`outfit_id`（W001–W030）、`dress_side`（left/right，按画面位置）、互斥的 `scene`（原背景／上传场地／后续真实场馆）。原背景不得带场地图，不设左右肖像字段。
客户端不能指定服装路径／URL、Key、Base URL 或任意模型名。服务端从唯一清单读取套装。响应一张已验证图片、真实 MIME、实际模型和请求标识；统一错误封装，不含原始上游正文或敏感配置。
核心接口改为有序角色参考图，每图含角色、字节和真实 MIME，另含提示词与输出规格。四张必填参考是合照、婚纱、男装、男鞋特写；加可选场地图最多五张。不支持完整参考能力必须报错，不得丢图继续。生成器、安全服务、素材读取器构造注入。
