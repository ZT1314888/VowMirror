# 28 张预设姿势的清单与随机生成

## 决策与证据

本次按用户确认的分类接入：22 张使用动作文字，6 张使用线稿与专用动作文字。
P001、P021 的最近一轮文字样本支持文字路线；其余分类结合线稿中的支撑、遮挡与接触关系推断。
P007 结合此前文字、线稿加动作文字的样本选择混合路线，最近一次文字超时不作为画质失败。
这些小样本不证明全库的稳定性，所有姿势继续标记为 `unverified`。

最近对照的带图组使用通用线稿指导，没有逐姿势动作句；不能据其方向偏差断定混合路线较差。
本次两种路线均有专用动作描述，目标是保留主动作、画面方向和接触关系，允许衣摆与关节角度自然变化。

## 唯一配置来源

[素材清单](../../assets/wedding/manifest.json) 升级为版本 2，每个姿势增加两个必填字段：

| 字段 | 含义 |
| --- | --- |
| `mode` | `text` 或 `lineart_text`，决定是否附加该条目的受控线稿 |
| `action` | 专用英文动作描述，明确人物角色、画面方向、接触点及必要的支撑关系 |

公共身份、服装、肢体及鞋履要求保留在后端共享提示词中。
清单条目只描述自身动作，不复制公共模板；代码不另存混合姿势编号表或动作句。
Go 与 Node 使用同一组正反契约用例，拒绝缺失字段、空动作、非法策略。
旧版清单不自动补字段或回退，必须随应用更新到版本 2。

## 请求与失败行为

用户发起一次生成后，后端读取并校验清单，从候选中抽取一次，再按选中条目组装请求。
没有额外模型分类调用，也不把全部姿势一起上传。重复生成允许再次抽到同一姿势。

基础四图为合照、婚纱、男装及男鞋特写；可选场地图排在其后，混合路线的线稿排在最后。
因此文字路线发送四或五图，混合路线发送五或六图。提示词按实际角色顺序计算场地和线稿编号。
明确允许人物重新摆姿，删除旧的原合照左右站位锁定；线稿只约束动作，不替换身份或服装。
肢体要求允许衣料自然遮挡，不要求为露出腿脚缩短婚纱。

随机源由构造依赖注入；生产使用系统密码学随机源，测试使用确定性输入。
空候选池、非法清单、随机源失败、所选线稿缺失或损坏均明确失败，不另抽一张或退成无姿势生成。
这些准备失败发生在模型发送及尝试计数之前。

浏览器请求字段保持合照、套装编号与场地，不接收客户端姿势、提示词或素材路径。
公开目录仍只输出版本、服装及场馆编号和名称；版本随清单变为 2，不输出姿势内部策略。
线稿通过 Compose 只读挂载，继续被 Git 与 Docker 构建上下文忽略，HTTP 不提供实图访问。
人物上传、生成结果及提示词全文不写日志。

## 验证边界

自动测试覆盖 28 个候选的确定性遍历、数组重排、随机失败与空候选池。
服务测试验证每次只选一次，文字路线不读取线稿；真实本地 TLS multipart 覆盖四、五、六图及准确动作句。
缺图、损坏、错误顺序的错误路径验证不调用模型、不扣尝试。
Go 与 Node 清单校验、构建及浏览器烟测通过后记录本轮结果；受控验证不证明真实模型效果。

本次未授权付费模型调用、提交、推送或公开部署。
