## 诊断实现

上轮错误被多个验证分支统一折叠为 `ErrResult`，阶段记录无法指出具体拒绝条件。
本轮属于共享结果验证与诊断传播的结构性改动，保持原有接受／拒绝条件、业务码和用户错误文案。

- 结果验证模块（实验工作树 `backend/internal/logic/tryon/result_image.go`）集中定义 16 个具体原因码及未分类原因。
  受控错误仍兼容 `errors.Is(err, ErrResult)`，错误文本保持原值，不附带原始错误或响应内容。
- 共享图片验证（实验工作树 `backend/internal/imagevalidate/errors.go`）区分损坏数据和 MIME 冲突，复用原有唯一解码实现。
  包装错误仍可通过 `errors.Is`、`errors.As`取得原上传 API 错误，业务码及文案保持原值。
- 适配器逐项记录解析、交付、元数据及图片拒绝原因；服务边界对注入生成器的输出复用相同分类。
  错误对象携带不进入 JSON 的内部原因字段，状态事件复用已观察的阶段、时间和原有错误分类。
  没有阶段观察时只记录受控日志并保留原错误终态，脚本明确标记缺失诊断，不伪造阶段。
- SSE 状态事件（实验工作树 `backend/internal/cmd/generation_stream.go`）和诊断日志增加可选 `result_validation_reason`。
  未分类错误及 SSE 交付大小限制出口明确记录 `unclassified_result_failure`；未知非空原因不会原样输出。
- 实验脚本（实验工作树 `scripts/pose-evaluation.mjs`）仅将固定原因码写入 JSONL 的 `resultValidationReason`。
  `INVALID_MODEL_RESULT` 缺少合法原因时记录 `diagnosticMissing: true`；未分类或缺失原因不能算具体诊断通过。
  普通失败继续完成另一组预定请求；供应商鉴权或限流在记录后停止。脚本不自动重试。

固定具体原因码覆盖以下分支：

| 类别 | 原因码 |
| --- | --- |
| 解析与交付 | `invalid_json`、`provider_error_field`、`image_count_mismatch`、`unexpected_image_url`、`missing_image_data` |
| 元数据 | `output_format_mismatch`、`output_size_mismatch`、`output_quality_mismatch`、`provider_model_mismatch`、`unsafe_provider_metadata`、`provider_request_id_conflict` |
| 图片 | `invalid_base64`、`invalid_image_data`、`image_limits_exceeded`、`image_format_mismatch`、`image_dimensions_mismatch` |

诊断状态、日志及 JSONL 不保存供应商响应体、照片、Base64、凭据、地址或未经校验的供应商元数据。
成功成片仅由实验客户端保存到 Git 忽略的本机目录，应用服务器不持久化照片或结果。

## 本轮验证

Docker 定向测试覆盖全部 16 个具体原因、缺省元数据、合法日期型号快照、冲突及拒绝顺序。
非法响应头仍优先于非成功 HTTP 状态，超大响应仍是上游错误，nil 结果仍保持原业务错误。
服务边界、SSE 大小限制和未知原因均有明确断言；共享上传错误继续核验原业务契约。

38 项实验脚本测试通过，覆盖原因白名单、未知／缺失原因、后续事件不清空已有原因、请求上限及停止策略。
受控 TLS 经真实 HTTP 处理器生成错误 SSE，再由实验脚本写入并读回 JSONL，具体原因完整保留。
同时检查阶段观察、HTTP／SSE、服务日志和 JSONL 没有敏感数据泄露。
受控响应只证明接口及诊断链路，不证明真实模型效果、速度或费用。

Docker 全量 Go 测试、格式检查、`vet`、构建和 Node 检查通过。

应用构建与离线 Chromium 烟测通过，覆盖四种宽度、授权、上传场地、生成、取消和刷新后的清理。

加入 P007 没有带来明确整体改善，该张结果反而出现额外足端；一组样本不足以推断姿势图的稳定收益或损害。
继续以文本模板作为主技术方向，姿势图保持实验对照；前序不同条件的结果不合并计算胜率。
